Version 0.12.1 addresses the native-sharing architecture gap:

5. **Persistent native exact-window capture** — `computer.share.start` now owns one ScreenCaptureKit `SCStream` on macOS or a project-owned Windows Graphics Capture `CreateFreeThreaded` frame pool on a dedicated MTA owner thread. Each native callback writes to a capacity-one source mailbox with its own sequence/drop metrics; PNG conversion and the acknowledged transport mailbox remain separately bounded. macOS resizes update the existing stream in place under a host-time- and dimension-gated geometry epoch, instead of replacing the share or pairing a transitional frame with new bounds. Capture is no longer stopped by the controller mutex during an action, but publication and the composited pointer still resume after command serialization. This is shared-session operation with before/after input invariant checks, not a VM, RDP desktop, PiP view, native picker, or separate input seat; matching samples do not prove zero interruption. Source contracts are green; packaged macOS and real-Windows runtime evidence is still required.
6. **Post-cancellation and client-teardown authority quarantine** — every outcome-unknown computer owner now installs a helper-session publication gate under the same lock as the public frame and screenshot. Handler Drop synchronously fences replay before releasing the action lock; the single-claimer settlement installs quarantine before caching 504, and a different queued callId helps settle before it can read or relay old authority. Negotiated late frames are acknowledged but discarded; stale status replies are suppressed in both state and command results; unrecovered mutations fail server-side; recovery requires an explicit share-free observation or a successful fresh share start; and frames plus capture errors stay bound to the exact approved share epoch. The retired-ID set is capped at 256 and saturates fail closed with stable `COMPUTER_SHARE_SESSION_EXHAUSTED` / `reconnect` recovery. Integration coverage proves both a post-202 old frame and a post-REST-timeout old frame were processed and acknowledged without resurrection, proves no replay-504 or fresh-waiter relay can precede teardown quarantine, then proves one-shot recovery, exact-new-share recovery, old/mismatched frame and error quarantine, safe stop, and replacement-session preservation.
7. **Exact macOS receiver and two-application focus lease** — WindowServer inventory establishes that the selected `(PID, CGWindowID)` remains an eligible, on-screen, non-minimized exact target; sibling count never establishes input authority. Keyboard dispatch instead requires the application's exact [`AXFocusedWindow`](https://developer.apple.com/documentation/applicationservices/kaxfocusedwindowattribute) to match that target, and text additionally resolves [`AXFocusedUIElement`](https://developer.apple.com/documentation/applicationservices/kaxfocuseduielementattribute) back to the same window. A different-process focus-preparing action leases both the user's exact front AX window and the target application's prior AX window, re-proves the user through a foreground-PID → focused-window/`AXFrontmost` → foreground-PID sandwich before each new focus-capable mutation, and restores and bounded-polls both applications. Native text repeats the exact receiver and focused-element proof after event construction immediately before every scalar key-down; loss after an earlier scalar is outcome-unknown and is never automatically retried. These bounded proofs narrow, but cannot make atomic, the interval between the final AX read and private event post. Source/unit coverage exists; the deterministic live wrong-sibling-at-dispatch negative remains explicitly unproven below.

Version 0.12.2 hardens the pre-freeze candidate around three audit findings and one live-evidence UX finding:

8. **Page-indicator fail-closed reuse** — the public host and a private closed-shadow marker are random per document; shadow-important rules suppress critical generic host, pseudo-element, and backdrop CSS, while accessibility or View Transition ambiguity fails closed. Every same-tab controlled action requires the host to remain the direct document-element child, re-tops it, and obtains a bounded render/layout/computed-style plus document/closed-shadow acknowledgement except the browser-process dialog resolver. Chrome resolves exact `:root`, pins the marker's innermost closed-shadow host, rejects intermediate light/shadow wrappers, requires raw ordered top-layer membership with no later same-root node, verifies five `ignorePointerEventsNone` point hits, and repeats host/root ancestry plus accessibility-critical attributes in the final phase. A top-layer revision seqlock, separate content-loss generation captured before renderer delivery, and shared 1.5 s/512-work proof bound handle own-event churn and same-revision loss. The content watchdog attempts a sample every 500 ms when idle; an uncleared browser top-layer event or indicator loss retains an absolute 3 s service-worker deadline plus scheduling/transport timing. These experimental Chrome 140+ DOM dependencies are not compositor, physical-pixel, or atomic-with-input proof; Chrome's browser-owned warning and Cancel remain authoritative.
9. **Trusted saved-token removal and approval identity** — the extension popup now exposes a confirmed **Clear saved token** action. It is accepted only from the popup URL, synchronously invalidates the controller and cancels deferred work, revokes control, clears exact-session/connection-bound approvals and their badge, disconnects, removes rather than blanks the storage entry, enters not-configured state even if Bridge was paused, and verifies `tokenConfigured: false`. This is not rollback after a Chrome side effect has crossed dispatch. Disabling Bridge control still intentionally preserves the credential.
10. **Conservative Windows readiness** — `inputReady` and `semanticReady` require a non-Session-0 helper plus a successful read-only input-desktop/foreground/focus/cursor snapshot. Probe failure reports false without input or a prompt; provider-specific action failures remain authoritative after a passing probe.
11. **Platform-truthful key grammar** — browser `page.key` and native `computer.key` retain one normalization syntax but now document distinct CDP, macOS, and Windows delivery subsets, including Windows global/secure shortcut refusal.

Version 0.12.3 is a live-found recovery and acceptance-integrity patch:

12. **One-shot versus streamed observation authority** — `computer.observe` deliberately produces a one-shot frame with no top-level share provenance, even while its nested status reports a live persistent share. The server now validates those as two separate domains: a one-shot may publish only when its nested active share matches the approved epoch, a streamed frame still requires a complete top-level `(shareId, sourceSequence)` pair plus the same nested ID, and partial, retired, mismatched, or unacknowledged stream identities remain refused. This fixes the exact post-cancellation sequence that stopped the 0.12.2 candidate without converting nested status into frame authority.
13. **Truthful stock-Chrome acceptance surfaces** — the Chrome control connector may prepare and inspect stock Chrome only before Local Browser Bridge attaches or after it fully detaches. Both are debugger clients and Chrome permits only one debugger owner per tab, so Chrome control cannot drive or capture an active bridge lease. During that lease, ordinary commands run through the Local Browser Bridge API matrix itself; Chrome WebUI, browser chrome, the native folder picker, extension popup, debugger warning, Chrome Cancel affordance, and all active-lease screenshots require a separately authorized app-level Computer Use surface or a human operator. The protocol records the chosen surface per step, requires confirmation before persistent security changes, restores Developer mode, Full Access, token, and extension disposition to their captured initial state, and makes manual screenshot review a later human attestation bound to already-sanitized bytes rather than an agent assertion.

Version 0.12.4 is a Windows helper-lifecycle and acceptance-integrity patch found by the exact 0.12.3 candidate run:

A failed `tokio::signal::ctrl_c()` registration now logs once and stays pending instead of selecting the shutdown branch, terminating the worker, or exiting the supervisor. One pinned shutdown future is reused across worker polling and restart backoff; deterministic tests prove success completes and registration failure remains pending.
15. **Protocol-bound worker readiness** — the helper hello now requires a nonzero OS `processId`. Windows acceptance binds that authenticated PID to exactly one direct child using the canonical helper image path, verifies the interactive Windows session, requires the same protocol session and PID across consecutive polls, then completes a read-only `computer.status` round trip. Unrelated children are ignored; multiple exact-image workers, supervisor exit, Toolhelp/image-query failures, PID/session mismatch, and timeout fail closed with sanitized, stage-labelled topology transition history. The generic wait no longer catches and erases arbitrary exceptions. Both Windows CI and release jobs parse the live runner, compile its embedded C# under Windows PowerShell 5.1 and PowerShell Core, and exercise exact parent/image/session lookup plus suspended Job-owned launch, resume, termination, and accounting before live acceptance.

Version 0.12.6 is an evidence-authority repair found by the exact 0.12.5 macOS run:

17. **Same-epoch streamed authority for live-share cleanup** — the native-text evidence flow no longer calls one-shot `computer.observe` while its persistent share is active. It waits for a later server-published streamed frame whose top-level `shareId` equals the original lease, whose `sourceSequence` equals the sampled transport record, whose geometry is settled, and whose semantic restore element is present; only that frame may authorize the cleanup `computer.setValue`. Version 0.12.7 is an acceptance-authority repair found by the exact 0.12.6 Windows run:

18. **Click-bound Windows foreground arming** — fixture readiness no longer treats `Shown`, `TopMost`, or an unchecked WinForms `Activate()` callback as proof of the global foreground. Only after helper topology, recovery-event readiness, and exact target selection does the runner post a fresh test-only `WM_APP` generation to the exact sentinel. Before prompting the operator, it separately waits for a bounded delivery receipt proving that exact generation was processed once, the button is enabled, the same-thread fixture-owned root/button topology still holds, and input is either untouched or already one internally consistent acknowledgement. Accepting the latter avoids rejecting a valid click made as soon as the button visibly enables; the prompt explicitly says not to click again if the button already says **ARMED**. The button accepts mouse down only while `GetForegroundWindow` equals the sentinel and the sentinel UI thread's `GetFocus` equals the exact button; focus loss, deactivation, or a new generation clears the pending press. Mouse up must repeat the exact generation, button, point, foreground, and focus checks before acknowledgement, and total left-down/up attempts must each remain exactly one through final invariants. The runner then requires three consecutive direct native samples with stable foreground, focus, OS-global cursor position, and input desktop plus exact equality at the arm-to-baseline recapture. Persistent cursor motion resets stability and eventually reaches the bounded timeout; missing clicks, stale acknowledgements, duplicate counts, focus mismatch, unavailable probes, and timeout fail closed. The proof retains only generations, counts, equality/availability booleans, and sample totals—never raw window handles or cursor coordinates. No `SetForegroundWindow`, `AttachThreadInput`, `SendInput`, synthetic Alt key, automatic click, or focus-stealing loop was added. A trusted human or separately authorized Computer Use surface performs the one explicit setup click, then must stop interacting while product actions run. This is an acceptance receipt inside a trusted interactive session, not cryptographic provenance of physical input; untrusted same-integrity window-message injectors are outside that evidence boundary.

The fixture increments a monotonic state-publication generation on every state write. Each accepted arm sample must use a newer publication than the delivery receipt and the prior accepted sample; the baseline must use a further publication, and every later invariant comparison advances a run-global publication boundary. A stalled or replayed valid JSON snapshot therefore cannot satisfy stability or hide a later duplicate request/click. After arming, the runner also re-binds the original authenticated helper session and PID to the same exact-image direct child and completes another `computer.status` round trip before the first baseline observation. A fixture writer stall or helper restart during the human wait fails closed before any observation, capture/share, input, or other effectful product action; the earlier protocol-binding `computer.status` is deliberately read-only.

## Version 0.12.8 macOS receiver acceptance cells

The candidate treats window eligibility, application focus, and the actual input receiver as three different facts. An all-window inventory must still prove exact owner/layer/geometry/on-screen eligibility, but [`AXFocusedWindow`](https://developer.apple.com/documentation/applicationservices/kaxfocusedwindowattribute)—not [`AXMain`](https://developer.apple.com/documentation/applicationservices/kaxmainattribute), z-order, title, size, or sibling count—authorizes a keyboard receiver. Text also requires [`AXFocusedUIElement`](https://developer.apple.com/documentation/applicationservices/kaxfocuseduielementattribute) to resolve through the element's [`AXWindow`](https://developer.apple.com/documentation/applicationservices/kaxwindowattribute), top-level window, or bounded ancestry to the selected ID. AX calls use bounded per-call messaging timeouts and whole-proof deadlines; Apple's [Accessibility API declarations](https://developer.apple.com/documentation/applicationservices/axuielement_h) do not provide an atomic focus-proof-and-event-post primitive.

For a different-process target, the phase lease records the user's foreground PID and exact focused/frontmost AX window and the target application's prior focused AX window. Before each new focus-capable mutation it samples foreground PID → exact `AXFocusedWindow` plus [`AXFrontmost`](https://developer.apple.com/documentation/applicationservices/kaxfrontmostattribute) → foreground PID, while target focus is independently proved and both remembered windows are restored and bounded-poll verified. This is a dual user/target lease, not “activate and hope.” The acceptance cells below remain separate so a positive same-PID run cannot accidentally satisfy an adversarial dispatch gate.

| Adversarial cell | Required result | Evidence state for the 0.12.8 candidate |
|---|---|---|

## Remaining boundaries

- Chrome's native warning depends on an actual non-suppressed `chrome.debugger` attachment. The exact published 0.11.1 stock-Chrome run now proves the warning and independent page pill simultaneously; a screenshot of only the page pill would still not prove it.
- Chrome's Cancel action can terminate all debugger clients owned by that extension. Local Browser Bridge holds one controlled-tab attachment, and the exact published 0.11.1 run now proves the native trigger: the unique PID-scoped Cancel click produced `canceled_by_user`, revoked the lease, removed the overlay, latched `humanPaused`, and refused the next remote start. The run used an intentionally ephemeral CDP-installed extension, so persistence across a full Chrome restart remains unproven.
- The human-pause latch is proven live through both human surfaces exercised so far: the in-page Stop click produced `released_by_user`, while native Chrome Cancel produced `canceled_by_user`; both revoked the lease and refused subsequent remote control with `HUMAN_CONTROL_PAUSED`. The extension popup's **Release control** is the remaining unexercised release surface.
- Since 0.11.1 a connector failure's HTTP status is derived from its taxonomy class, so a human pause is 423 rather than 500. Statuses the server produces for its own refusals are unchanged, and `INVALID_SANITIZER_STATE` remains the one 500 the API can answer. Clients that branched on 500 to mean "retry or alert" must branch on the taxonomy instead.
- The page overlay cannot run on restricted `chrome://`, `edge://`, extension, or protected pages. Those pages also remain outside extension control.
- Open shadow roots are covered. The published 0.11.0 bundle proves one genuine depth-one OOPIF: child-session routing, provenance, coordinate translation, isolated-world proof, and a trusted click. The exact published 0.11.1 boundary run additionally proves a top-level `same_process_frame` report and live `FRAME_ACTION_UNSUPPORTED`, while its 17/19 result exposes the non-recursive depth-two defect. Version 0.11.2 recursively arms only routing-verified child sessions; a local packaged candidate passed 22/22 with a depth-two merge and trusted click. This is not cross-origin semantic parity or published repair proof. Same-document-navigation survival remains harness-only, nested in-process owners are not completely reported, and the exact `session_routing_unverified` result is an explicitly simulated stripped-session counterfactual rather than an identified Chrome behavior. Chrome 118–124 reject child-session routing because the schema lacks `sessionId`; Chrome 125 added the routed form.
- Same-origin and same-process iframes are still not merged, and only `page.click` and `page.hover` act inside a frame. `page.fill` and `page.select` refuse a frame-scoped ref with `FRAME_ACTION_UNSUPPORTED`; `page.key`, `page.scroll`, `page.typeText`, and `page.clickAt` take no `ref` at all. Top-document in-process iframe owners are reported as `same_process_frame`; an in-process owner nested inside an attached child is a stated reporting gap because the frame agent does not publish nested owners.
- The 0.11.2 lease recursively applies `Target.setAutoAttach` to each routing-verified child session because the CDP setting is direct-only. Non-`iframe`, unknown-parent, blank, over-count, and over-depth targets are detached on arrival; nested detach removes the recorded subtree; child sessions still ride the one controlled-tab debugger attachment; and the in-frame agent remains read-only in a nonce-keyed isolated world. A third-party embed is inside the attachment's blast radius in a way it was not before 0.10. See [../SECURITY.md](../SECURITY.md).
- A pending dialog no longer revokes the lease, but the guarantee is scoped: it covers renderer-blocked probes, dispatches, held-input releases, and service-worker recovery. An explicit stop, a human pause, the lease TTL, a recovered candidate that fails the restart's own fail-closed rules, and any failure observed with no dialog pending all still revoke — and nothing is forgiven permanently, because the record is cleared the moment the dialog resolves and the very next check catches a document that really did change.
- The browser extension manifest grants broad HTTP(S) and optional file host access before its Full Access/Safe-mode policy runs. Safe mode is an extension-owned allowlist/approval policy, not a Chromium host-permission boundary, a separate profile, or a sandbox. Loopback authentication, stale-state checks, and visible control do not make prompt-injected page content trustworthy.
- Native target selection is programmatic in the authenticated bridge control page. It does not invoke Apple's [`SCContentSharingPicker`](https://developer.apple.com/documentation/screencapturekit/sccontentsharingpicker) or the Windows system picker, so an OS capture indicator/stop affordance is not evidence of per-window input consent.
- Once the helper is running with the relevant operating-system grants, selecting a supported application window grants the current helper session its fixed command authority. There is no helper-owned native per-application approval ledger, and browser Safe mode does not govern native applications. Stop the helper when that authority is not needed.
- The native helper has no persistent native input-authority indicator or trusted global Stop/Esc handback. System capture indication is independent and does not report or revoke keyboard/pointer authority; the composited helper cursor is visible only in returned frames.
- macOS background delivery depends on private, unsupported SkyLight interfaces. The 0.12.28 candidate retains exact `AXFocusedWindow` receiver proof, focused-element ownership for text, a dual user/target focus lease, a private `CGEventSource`, and a frozen per-architecture artifact-route audit, but there is still no atomic public primitive joining the last proof to the private event post. `SLEventPostToPid` exposes no acceptance return. Unsupported OS/framework combinations must refuse rather than switch to global input.
- Windows UIA compilation is not representative Windows runtime proof. The v0.12.8 Windows run delivered its click-bound arm request but received no click and stopped before its baseline, while v0.12.9 never reached Windows. The click-bound arm remains an acceptance precondition, not a production capability or runtime pass; a native Windows fixture must still complete on v0.12.28. Its Raw Input and low-level injected-flag epochs cannot prove human/physical provenance and can have integrity, remote, or virtual-input blind spots.
- Exact-window sharing prevents unrelated-window capture but does not isolate memory, credentials, app state, or OS permissions from the user's session.
- The candidate artifacts are not Microsoft publisher-signed or Apple Developer ID-signed/notarized. GitHub provenance and SHA-256 checksums protect source/workflow provenance and byte integrity; they do not supply OS publisher identity, SmartScreen reputation, or Apple notarization. An ad-hoc macOS app signature is not notarization, and user documentation must not instruct people to bypass platform warnings.
- Deliberately deferred beyond 0.12.28: native content picker/PiP, same-process iframe merging, frame-scoped text entry and scrolling, frame-aware `page.clickAt`, PUSV-style pixel-diff preflight, an MCP facade, set-of-marks visual annotation, a compressed video transport, and an isolated OS input session. Each stays a stated boundary rather than a partial claim.

## Acceptance rule

Do not mark a versioned deployment—including the 0.12.28 candidate—complete until release-specific evidence exists, the full Rust/extension contract suite passes, both target artifact sets are verified, and the relevant real-browser and native-helper paths prove fail-closed behavior. The checked-in [v0.12.8 macOS record](../evidence/v0.12.8/computer/README.md) is a real 187/187 exact-candidate pass, but it was never published and cannot substitute for a later candidate. Its [interactive-Windows attempt](../evidence/v0.12.8/computer/attempts/withdrawn-532d603-windows-foreground-arm-timeout/README.md) stopped before the baseline, and Chrome never started. The [v0.12.9 macOS attempt](../evidence/v0.12.9/computer/attempts/withdrawn-db624da-macos-semantic-hardware-cursor-change/README.md) then failed closed once at `semanticSetValue` because the historical `hardwareCursorUnchanged` sample changed; the record could not identify the mover, and Windows/Chrome were not run. Version 0.12.28 must use fresh exact artifacts, complete separate quiet and deliberate-concurrency macOS lanes with the exact app-share receipt chain, record its click-bound Windows arm and pointer-monitor boundaries, complete real interactive-Windows capture/input, and exercise browser indicator-loss and saved-token handback through their documented control surfaces. The exact packaged macOS helper slices must pass the forbidden-global-API and targeted-dynamic-symbol audit. Earlier negative and withdrawn candidates remain diagnostic history. The live wrong-sibling-at-dispatch negative stays unproven until it is exercised safely; a nearby positive, source contract, API acceptance, or single screenshot cannot silently satisfy it.

For the exact published 0.11.1 artifacts, both halves of the real-Chrome Cancel clause are now satisfied. A unique PID-scoped native click supplied the browser-owned trigger; `chrome.debugger.onDetach` reported `canceled_by_user`; the lease and overlay disappeared; `humanPaused` latched; and the next remote start was refused with HTTP 423 `HUMAN_CONTROL_PAUSED`. This does not turn the unpublished 0.11.2 candidate into a deployment and does not prove full-browser-restart persistence: the stock-Chrome evidence installation was intentionally ephemeral and removed at cleanup.

Version 0.10 is the worked example of why that rule is written this way round. Its contract suite was green, its release was reproducible and attested, and its dialog gate was still broken on every real browser it met, because the suite injected the pending dialog before the gate instead of racing it. A green suite therefore licenses a live run; it never substitutes for one. Version 0.11.1 repeated the lesson twice: a Stop-button run found the HTTP 500 taxonomy/status mismatch, and the later boundary run found that a manually injected depth-two harness had hidden the root-only auto-attach defect. The 0.11.2 contracts now drive dynamic child events and the final local packaged candidate passes the live nested scenario, including the lease-sticky negative-routing behavior in contracts, but immutable release proof, popup Release, full-browser-restart persistence after Cancel, and Windows UIA runtime remain explicit gates. The exact published Chrome Cancel and macOS-helper paths are now live-proven rather than inferred from contracts.
