# Release process

> This page describes CI-hosted acceptance, which replaced the prior
> two-machine operator acceptance harness (tagged
> `archive/operator-acceptance-harness-0.12.68` before removal; see
> [Release-attempt history](../history/release-attempts.md) for why it was
> replaced). It is verified against `.github/workflows/acceptance.yml`,
> `.github/workflows/deploy.yml`, `.github/workflows/publish.yml`, and
> `scripts/ci-acceptance.mjs`; re-check those files after changing any of
> them and update this page if they differ.

In this repository, "deploy" means finishing the entire release operation:
build a candidate, let acceptance verify the packaged artifact, and only then
publish it as an immutable public GitHub Release. Publication is a separate,
manual workflow so a failed or unverified candidate never creates a tag,
Release, or protected-environment deployment.

## Two-phase workflow

```text
main (green commit)
    |
    v
deploy.yml — build the candidate            (Windows, macOS, extension)
    |
    v
CI-hosted acceptance                        (reusable workflow: Chrome for
    |                                         Testing + native helper on
    |                                         windows-latest and macos-26)
    v
schema-4 acceptance receipt (attested, bound to this exact candidate)
    |
    v
publish.yml --dry_run=true                  (fetch and verify the receipt,
    |                                         preflight only; no tag, no
    |                                         Release)
    v
publish.yml --dry_run=false                 (create the tag, publish the
                                              Release, redownload and verify)
```

The same CI-hosted acceptance workflow is reused in two modes: **source
mode**, run by `ci.yml` on every pull request against freshly built binaries,
so an acceptance regression is caught before merge instead of only at release
time; and **artifact mode**, run by `deploy.yml` against the frozen,
packaged candidate bytes that will actually be published, so acceptance
proves the shipped artifact, not just the source tree.

### 1. Build the candidate

Dispatch `deploy.yml` from a green `main` commit. It builds the Windows and
macOS binaries, packages the extension, and assembles the canonical
`SHA256SUMS.txt` — the same shape as before: a Windows server executable,
Windows helper executable, macOS universal archive with helper app, matching
extension ZIP, and checksum manifest. This phase creates no tag, draft, or
Release.

### 2. CI-hosted acceptance

Runs automatically against the frozen candidate artifact on `windows-latest`
and `macos-26` GitHub-hosted runners: Chrome for Testing plus the native
helper, exercising the browser, computer, and shell surfaces without a human
operator. A pass produces a schema-4 acceptance receipt, uploaded as a
workflow artifact and bound to the exact candidate artifact, source SHA, and
workflow run/attempt — the same binding discipline the prior harness used,
now generated by CI instead of requiring an interactive Windows session and a
human at the keyboard.

### 3. Publish

Dispatch `publish.yml` with the candidate's identity: `version`, `source_sha`,
`candidate_run_id`, `candidate_run_attempt`, and `dry_run`. The workflow
fetches and attests the receipt itself from the candidate run's artifacts —
you never hand it the receipt directly:

- `dry_run: true` reconstructs the candidate, verifies the exact asset
  inventory and attestations, and validates the receipt — without creating a
  tag or Release. Use this to check a release is ready before committing to
  it.
- `dry_run: false` additionally creates the annotated `vVERSION` tag,
  publishes the Release with all assets, and redownloads and verifies every
  published asset byte for byte.

Only the real-publish job uses the protected `release` environment.

## What fails closed

- A candidate that has not passed CI-hosted acceptance has no receipt, and
  `publish.yml` refuses to run without one.
- A receipt bound to a different candidate artifact, source SHA, or workflow
  run/attempt than the one being published is rejected.
- `dry_run: false` still redownloads and verifies the published bytes after
  tagging; a mismatch is a release-process bug to fix before the next
  attempt, not something to work around.
- Repository policy is part of the boundary: the tag ruleset allows only the
  first creation of `refs/tags/v*`, never update or deletion, and the
  protected `release` environment requires its configured approval.

## Bump the version

```bash
bash scripts/bump-version.sh <new-version>
bash scripts/audit-versions.sh
```

Aligns the Rust package version, `Cargo.lock`, the extension manifest
version, and the extension library version in one step, then verifies them.
Commit the result before dispatching `deploy.yml`.

## Evidence-commit rules

An acceptance run's evidence (screenshots, logs, the receipt itself) is a
workflow artifact, not a repository commit — see [evidence/README.md](../../evidence/README.md)
for why `evidence/` in this repository is frozen history rather than a
growing directory. Never record a credential, bearer token, personal path, or
raw browser/API data in retained evidence.

## Manual local build (not a release)

```bash
bash scripts/verify-release-assets.sh VERSION dist
```

On a suitably configured macOS host, `scripts/deploy.sh` can produce a local
cross-platform candidate for early testing; official Windows artifacts
require the MSVC target through `cargo-xwin` or a native Windows build. Local
outputs are never release proof unless their SHA-256 values match the frozen
workflow candidate.

See [Verify a release](../VERIFY_RELEASE.md) for the consumer-facing
provenance-verification flow, and [Architecture](../ARCHITECTURE.md) for
component boundaries.
